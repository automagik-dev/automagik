# Automagik repository contract

Automagik holds the DeepSeek Harness (DSH) plugins every Automagik product builds on (the Bot team, `apps/bots-dsh`; the welcome, `apps/welcome-dsh`), the Automagik desktop app (`apps/desktop`), the Automagik Herdr pack (`herdr/`, imported from automagik-herdr with its history) and Pocket, the Android phone app (`apps/pocket/`, imported from automagik-pocket with its history; its desktop side, Pocket Link, is `herdr/mods/pocket-link`). Each part ships on its own lane of the one release (`docs/rfcs/0011-monorepo-parts-and-releases.md`).

- Bun for the repository's tooling (`scripts/`, `bun test`); cargo is the one exception, for the Rust crate `meter/usagemeter/` only, under the build rule in the Meter bullet. The plugins run on Node like DSH (`node --test`, esbuild) and install with Bun; a DSH profile is only ever installed through DSH (`dsh plugin`, pnpm); npm only for the desktop app's Electron tooling.
- Nothing is published to npm. Plugins ship as git sources pinned to release commits and as release tarballs.
- One version for everything (`bun scripts/version.ts`, the herdr pack's `herdr/package.json` and `herdr/mods/am-sidebar/VERSION`, am's `am/VERSION` and the meter crate's `meter/usagemeter/Cargo.toml` and `Cargo.lock` included; Pocket's Gradle reads the root `package.json`); never edit a version by hand. One tag, `vX.Y.Z`: no per-part tags. Minor and patch stop at 999, because Pocket's versionCode is `major*1_000_000 + minor*1_000 + patch`; `version.ts` refuses more, so bump the next part up instead.
- The herdr pack (`herdr/`, its own contract in `herdr/AGENTS.md`) is plain JavaScript Herdr loads as it is: no Bun, no install, no dependencies. Two Node floors: its users' runtime (the launcher `mods/am-sidebar/bin/run.sh`, `install.sh`) is Node 22.7 or later; its tests need the newest Node 22 (their stubs use `module.registerHooks`, 22.15+) or 24, and CI runs those two. Do not add a stub fallback for older Node, and do not raise the runtime floor for the tests' sake. Its gate, from `herdr/`: `node --test 'test/*.test.mjs'`, `node --check` on `mods/*/*.js mods/*/*.mjs mods/*/bin/*.mjs mods/*/pack/*.mjs scripts/*.mjs`, `shellcheck -s sh install.sh mods/am-sidebar/bin/run.sh mods/am-sidebar/bin/automagik-herdr`, `node scripts/catalog.mjs --check`, `node scripts/version.mjs check`, `node scripts/entries.mjs --check`, `node scripts/parts.mjs --check`, `node ../scripts/am-copies.mjs --check`; `herdr-app check <mod>` on a mod you changed, in a scratch app home. Its tests use temp homes and fakes (a stand-in `security` for am-quota's Keychain): never run them, the installer or `herdr-app` against a live Herdr install.
- A herdr-only merge is a herdr patch (`scripts/lane.ts`): the pack alone, no desktop build and no plugins. A release that rebuilt the pack attaches `automagik-herdr-pack-<v>.tgz` and its `.sha256` (name kept) and re-signs the rolling `herdr-lane` pointer (`pack.json` and `pack.json.sig`, `scripts/herdr-lane.ts`) with `HERDR_PACK_KEY`, the pack's own key, never `PLUGIN_LANE_KEY`. The pack's updater and `herdr/install.sh` read only that pointer, check it against `herdr/mods/am-sidebar/pack-keys.json` (install.sh's `TRUSTED_KEYS`, kept equal), then the tarball against its sha256; they never search the releases. Never print or commit a private key: tests sign with a key made per run, and the real key is made with `bun scripts/herdr-lane.ts keygen`, straight into the secret. A rotation is two phases (RFC 0011): keygen stages the new key in the slot `HERDR_PACK_SIGNER` does not name and a release ships its public key; only later does that variable switch. The pack never downgrades through the pointer: install.sh refuses one older than the installed version or recorded sequence, and the release refuses to post a lower sequence (it fails closed: an unreadable or unverifiable posted pointer stops it unless dispatched with `replace_unverified_herdr_pointer`).
- Pocket Link files (`herdr/mods/pocket-link`) belong to Pocket: the pack's installer and updater never write them, and it is never in the pack's `PACK_MODS`. A Pocket Link change still goes on the herdr lane; its bridge and chat tests (`node --test bridge/*.test.mjs chat/*.test.mjs find-node.test.mjs` from that folder; the chat folder rule shares its cases with am-sidebar in `herdr/test/fixtures/transcript-folder-rule.json`) are `ci.yml`'s `pocket-link` job.
- Pocket (`apps/pocket/`, its own rules in `apps/pocket/AGENTS.md`) is a part with its own lane: a Pocket-only merge is a pocket patch (`scripts/lane.ts`), the app alone, no desktop build and no plugins. Gradle needs a JDK 17 or later (JBR 21 works). Run its gate from `apps/pocket/android`: `JAVA_HOME=$HOME/Library/Java/JavaVirtualMachines/jbr-21.0.11/Contents/Home ./gradlew --no-daemon --max-workers=2 -Pkotlin.compiler.execution.strategy=in-process :app:assembleDebug :app:testDebugUnitTest :app:lintDebug`. On a shared host, run that through the host's gate wrapper (`sh <gate.sh> ./gradlew …`). Never run `./gradlew --stop`: it stops other sessions' daemons. A machine's `local.properties` (the SDK path) stays out of git.
- A release that rebuilt Pocket attaches `automagik-pocket-<v>.apk` and `latest.json` to `vX.Y.Z`, then replaces `latest.json` on the rolling `pocket-lane` release (never a prerelease run, never to a lower versionCode). Installed phones read only that file (`pocket.updateUrl` overrides it for a fork or a test server). `pocket-lane` is created as a prerelease, never edited by hand, and never marked Latest. The APK is signed with the release key from the secrets `POCKET_SIGNING_KEYSTORE` and `POCKET_SIGNING_PASSWORD`: never print them, never regenerate the key, and never change the app ID (`ai.namastex.automagik`). Moving `latest.json` or changing its fields needs an RFC (`docs/rfcs/0011-monorepo-parts-and-releases.md`, "Pocket").
- am (`am/`, `automagik.am`, RFC 0012) is the one command and the part every release carries, whatever its lane kind: `automagik-am-<v>.tgz` and its `.sha256`. An am-only merge is an am patch (`scripts/lane.ts`, from `am/part.json`'s `paths`). Plain JavaScript on Node 22.7 or later, like the pack; its gate, from `am/`: `node --test 'test/*.test.mjs'`, `node --check` on `*.js *.mjs bin/*.mjs lib/*.mjs`, `shellcheck -s sh bin/am bin/run.sh bin/automagik-herdr`, `node ../scripts/am-copies.mjs --check`. Its CLI and briefing are byte-equal copies of the sidebar's (the pack stays the source; `node scripts/am-copies.mjs --write` resyncs them): never edit a copy in `am/`. Every release signs the rolling `am-lane` pointer (`am.json`, `am.json.sig`, `scripts/am-lane.ts`) with `AM_LANE_KEY`, am's own key (two slots, `AM_LANE_SIGNER`), never `PLUGIN_LANE_KEY` or `HERDR_PACK_KEY`; its public keys are `am/am-keys.json`. While `am-keys.json` lists no key or that secret is not set, a release attaches am, posts no am-lane and warns; once keys are listed, a secret that is none of them stops the release before the tag. The post is its own job (`am-lane`, after the cut), so its refusals never stop the plugin lane or another job. The post fails closed (`replace_unverified_am_pointer`) and never posts a lower sequence; am refuses one too, and honours a test's own keys only for a `file://` release folder. Never print or commit its private key: `bun scripts/am-lane.ts keygen` puts it straight into the secret.
- A release that builds the meter signs the rolling `meter-lane` pointer (`meter.json`, `meter.json.sig`, `scripts/meter-lane.ts`) with `METER_LANE_KEY`, the meter's own key (two slots, `METER_LANE_KEY` and `METER_LANE_KEY_NEXT`; the variable `METER_LANE_SIGNER` names the one releases sign with), never `PLUGIN_LANE_KEY`, `HERDR_PACK_KEY` or `AM_LANE_KEY`; its public keys are `meter/usagemeter/meter-keys.json`. The installers carry copies of those public keys, never a private key: `herdr/mods/am-sidebar/meter-keys.json` (am's byte copy through `scripts/am-copies.mjs`) and `herdr/install.sh`'s `METER_KEYS`, kept equal by `meter-lane.test.ts`; keygen writes all three. The pack and am install usagemeter only through that pointer (RFC 0017 delivery 6): they verify its signature over the exact bytes against those keys before reading any field, refuse a sequence lower than the one the install record took, and take each machine's build and sha256 from it; the pack never checks the meter with `PLUGIN_LANE_KEY`'s or `HERDR_PACK_KEY`'s keys. The meter lane is held until a key is listed: no release builds, attaches or signs the meter before then, so there is no warn-only path. Once a key is listed, a release that builds the meter stops before the tag when that secret is unset or none of the listed keys (`meter-lane.ts check-key`). The attach job signs each build before it uploads anything; the post is its own job (`meter-lane`, holding no key), so its refusals never stop another lane, and a prerelease never moves it. It fails closed (`replace_unverified_meter_pointer`) and never posts a lower sequence. Making the key is the owner's (RFC 0017 delivery 5): `bun scripts/meter-lane.ts keygen` puts it straight into the secret; no one else runs it, sets or reads that secret, or lists a key in `meter-keys.json`. Never print or commit its private key: tests sign with a key made per run. A rotation is RFC 0011's two phases, as the pack's.
- No herdr-mod entry folder (any folder holding `mods/<name>/main.js`, `herdr/` included) may hold `layouts/`: herdr.dev skips the whole repository for one, and the skip deletes its listing. The pack's layout is its own top-level folder, `herdr-layout/`, a herdr.dev layout entry: `layouts/automagik.json` (herdr.dev lists a layout only from `layouts/` and ignores a `.json` at the folder's root), `RECIPE.md` and `preview.png`, and no `mods/` of its own (`scripts/entries.mjs --check`, RFC 0011).
- `herdr/` is the herdr.dev Community entry's folder; do not add a `herdr-mod` or `herdr-layout` topic to this repository until the owner opens the listing.
- Meter (`meter/`): usagemeter, the Rust token meter (`meter/usagemeter/`, `automagik.usagemeter`, imported from automagik-dev/usagemeter with its history, RFC 0017), ships on the meter lane. A meter-only merge is a meter patch (`scripts/lane.ts`, from `meter/usagemeter/part.json`'s `paths`): the meter alone, no desktop build and no plugins. The meter never makes a release more than it is otherwise: meter with herdr is a herdr patch that builds both, with Pocket a pocket patch, beside plugins a plugin patch. Whether a release builds it is `lane.ts meter`, measured from `lane.ts meter-since` (the version `meter-lane` names, else the newest stable release: a prerelease is never the base, so its meter is built again by the next stable release). The crate's top-level `*.md` and its `tests/` never ship, and a release's own bump of its two version lines (`Cargo.toml`, `Cargo.lock`, through `scripts/version.ts`) cuts no meter release. The key comes first: the lane is held (`lane.ts` `meterHeld`: no meter build, attach or post, and the crate ships nothing) until both hold: `meter/usagemeter/meter-keys.json` lists a key, and the query contract's `attribution.precision` (`meter/schema/query/v1/envelope.schema.json`) allows `actor_interval` (RFC 0021 delivery 2). A release that builds the meter attaches the four binaries `part.json`'s `artifact` names (`usagemeter-darwin-arm64`, `usagemeter-darwin-x86_64`, `usagemeter-linux-x86_64`, `usagemeter-linux-aarch64`; the Intel Mac build stays for good), `usagemeter.SHA256SUMS` and the build's signed `meter.json` and `meter.json.sig`, built on CI from the tag by `release.yml`'s `meter` jobs (`desktop-build.yml`'s sweep spares them): no meter build is ever public unsigned, a prerelease's included. Since the cutover (RFC 0017 delivery 6) the pack and am install it from the signed `meter-lane` pointer: no version or hash is pinned in the pack. `meter/statusline` and `meter/schema` still never ship (`NEVER_SHIPPED` keeps `/^meter\/(statusline|schema)\//`). The local tools (`meter/statusline`: the Claude Code status line and the limits logger that runs it as `claude-limits-statusline.mjs -- <status line>`) are plain Node with no dependencies, run from the owner's machine; their gate: `node --check meter/statusline/*.mjs` and `node --test 'meter/statusline/test/*.test.mjs'` (`ci.yml`'s `meter` job). The crate's gate, from `meter/usagemeter`: `cargo fmt --check`, `cargo clippy --all-targets --locked -- -D warnings`, `cargo test --locked` (`ci.yml`'s `usagemeter` job, Linux and macOS, on the toolchain it pins, plus `tests/install.sh` while the standalone installer exists). Before the tag, a release that builds the meter runs `cargo fmt --check`, clippy and `cargo test --locked` again, on Linux; not `tests/install.sh`, which stays CI's. The build rule: cargo runs only on the build host, one build at a time behind the host's shared gate lock, with `CARGO_BUILD_JOBS=4`; never as part of a gate on a contributor's laptop (`cargo fmt --check` builds nothing and may run anywhere); the OS matrix and the cross-target release builds run on CI only, never on the build host; a worktree's `target/` goes with the worktree.
- A package whose tests need `--test-force-exit` runs them through `scripts/test-guard.mjs`: that flag can cut a test file's results at process exit and still exit 0 (#422). The guard fails a run with no TAP plan, a plan short of its results, or a test file with no end-of-file summary (which includes a test file with no tests), and never retries.
- Generated client bundles (`client.js`) are committed: run `node scripts/build-client.mjs` in the plugin and commit the result.
- Plugin ids, routes, storage prefixes and the team's home are a public contract: installed teams keep their data there. Do not rename them.
- Omni-specific code still in the Bot team (the `omni_*` tool names, Omni as the Main Bot) belongs in Omni's plugins; move it there, not further in.
- Brand (`docs/brand/`): any work on a logo, a colour, type, a UI surface or brand art starts from `docs/brand/README.md` and uses its files and tokens. Never redraw a mark or invent a colour.
- Commits are conventional (`type(scope): description`); pull requests target `dev`.
- Do not start services, access production systems or send external messages without explicit approval.
